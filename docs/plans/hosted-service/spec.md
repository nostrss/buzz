# Hosted Buzz: 이메일 로그인과 셀프서비스 커뮤니티 생성

Status: ready-for-agent
Branch: feat/hosted-service (→ deploy)
Glossary: /CONTEXT.md
ADR: /docs/adr/0001-custodial-identity-keys.md

## Problem Statement

Buzz 데스크톱을 처음 켜면 "identity key를 만들거나 가져오라"는 화면이 나오고,
nsec 붙여넣기, 비밀번호 백업 파일, 폰 페어링 같은 선택지가 이어진다. 개발자가
아닌 사람은 여기서 멈춘다. 커뮤니티를 만들고 싶어도 "Create a community"
버튼은 Block이 운영하는 BuilderLab으로 가서 우리 릴레이에는 아무것도 생기지
않고, 우리 릴레이에 커뮤니티를 만드는 유일한 방법은 운영자가 서버에서 API를
직접 호출하는 것이다. 새 사용자 입장에서 슬랙처럼 "이메일 넣고, 팀 이름
정하고, 동료 초대"가 되지 않는다.

## Solution

이메일과 6자리 코드로 로그인하면 계정 서비스가 신원 키를 대신 발급·보관하고,
앱은 키 관련 화면을 하나도 보여주지 않는다. 로그인한 계정은 이름 하나로
`<이름>.app.pegboard.me` 커뮤니티를 만들 수 있고(계정당 1개), 초대 링크로 남의
커뮤니티에 들어갈 수 있다. 커뮤니티에 들어가면 upstream의 환영 채널과
에이전트 킥오프가 그대로 이어진다. 새 맥에서는 같은 이메일로 로그인만 하면
같은 신원으로 돌아온다.

## User Stories

### 가입과 로그인

1. 처음 앱을 켠 사람으로서, 이메일 하나만 입력하고 시작하고 싶다. 키, 백업,
   페어링이라는 말을 보고 싶지 않다.
2. 이메일을 입력한 사람으로서, 메일로 온 6자리 코드를 앱에 입력해 로그인하고
   싶다. 링크를 누르거나 브라우저를 오갈 필요가 없어야 한다.
3. 휴대폰에서 메일을 확인한 사람으로서, 맥의 앱에 코드를 그대로 입력하면
   되어야 한다. 어느 기기에서 메일을 열었는지는 상관없어야 한다.
4. 코드를 잘못 입력한 사람으로서, 남은 시도 횟수와 함께 다시 입력할 수 있어야
   한다. 5회 실패하면 코드가 폐기되고 새 코드를 요청해야 한다.
5. 코드가 만료된(10분) 사람으로서, "코드 다시 보내기"로 새 코드를 받을 수
   있어야 한다.
6. 코드를 여러 번 요청하는 사람으로서, 같은 이메일로는 분당 1회만 발송된다는
   안내를 받아야 한다.
7. 처음 로그인한 사람으로서, 로그인 순간 신원 키가 자동으로 발급되어 내가
   아무것도 하지 않아도 릴레이에 접속되어야 한다.
8. 다시 로그인한 사람으로서, 처음과 같은 신원(같은 pubkey)으로 돌아와 내
   프로필과 메시지가 그대로 내 것이어야 한다.
9. 새 맥을 쓰는 사람으로서, 같은 이메일로 로그인하면 같은 계정과 커뮤니티
   목록이 나와야 한다.
10. 앱을 다시 켠 사람으로서, 90일 동안은 로그인 화면을 다시 보지 않아야 한다.
11. 세션이 만료된 사람으로서, 이메일 코드 한 번으로 다시 들어갈 수 있어야
    한다. 데이터는 그대로여야 한다.
12. 로그아웃한 사람으로서, 이 맥에 세션과 신원 키가 남지 않아야 한다.
13. 기존 키가 이미 키체인에 있는 맥을 쓰는 사람으로서, 이메일로 로그인하면
    계정의 키가 그것을 대체해야 한다. 예전 키에 대한 질문을 받지 않아야 한다.
14. 사용자로서, 설정 어디에서도 nsec, npub, 키 내보내기, 키 가져오기를 보지
    않아야 한다.

### 커뮤니티 생성

15. 커뮤니티가 없는 로그인 사용자로서, "커뮤니티 만들기"와 "초대 링크
    붙여넣기" 두 가지만 있는 화면을 보고 싶다.
16. 커뮤니티를 만드는 사람으로서, 이름 하나만 입력하고 싶다. 이름이 곧 주소가
    된다.
17. 이름을 입력하는 사람으로서, 영소문자·숫자·하이픈 3~30자만 허용되고,
    대문자는 소문자로, 공백은 하이픈으로 바뀌는 것을 입력 중에 보고 싶다.
18. 이름을 입력하는 사람으로서, `<이름>.app.pegboard.me` 미리보기와 "사용
    가능 / 이미 사용 중" 표시를 입력 중에 보고 싶다.
19. 예약어(`app`, `auth`, `www`, `admin`, `api`, `mail`, `relay`)나
    하이픈으로 시작·끝나는 이름을 넣은 사람으로서, 왜 안 되는지 바로 알고
    싶다.
20. 커뮤니티를 만든 사람으로서, 만들자마자 내가 owner로 들어가 있고 upstream
    의 환영 채널과 에이전트 킥오프를 그대로 겪고 싶다.
21. 이미 커뮤니티를 하나 만든 사람으로서, 두 번째를 만들려 하면 "계정당
    하나"라는 안내를 받아야 한다. 초대로 여러 커뮤니티에 들어가는 것은
    제한이 없어야 한다.
22. 커뮤니티를 만든 사람으로서, 곧바로 초대 링크를 만들어 동료에게 보낼 수
    있어야 한다(upstream 기능 그대로).

### 초대와 참여

23. 초대 링크를 받은 사람으로서, 앱이 없으면 다운로드 안내를, 있으면 앱이
    열리길 원한다.
24. 초대 링크로 앱을 연 미로그인 사용자로서, 이메일 로그인이 끝나면 별도
    조작 없이 그 커뮤니티에 조인되어야 한다.
25. 초대 링크로 앱을 연 로그인 사용자로서, 곧바로 조인되어야 한다.
26. 커뮤니티가 있는 사용자로서, 다른 커뮤니티의 초대 링크를 붙여넣어 추가로
    들어갈 수 있어야 한다.
27. 멤버로서, 커뮤니티에서 나갈 수 있어야 한다.
28. 사용자로서, 커뮤니티 삭제 기능은 없으며 필요하면 운영자에게 요청한다는
    것을 안내받아야 한다.

### 운영자

29. 운영자로서, 팀 릴레이 `app.pegboard.me`를 멀티테넌트 릴레이로 승격하고
    팀은 그 릴레이의 커뮤니티 하나로 다시 시작하고 싶다. 기존 데이터는
    버린다.
30. 운영자로서, 어떤 `<이름>.app.pegboard.me`가 요청되어도 DNS와 TLS를 손대지
    않고 서비스되기를 원한다.
31. 운영자로서, 등록되지 않은 호스트명에는 인증서가 발급되지 않기를 원한다.
32. 운영자로서, 릴레이의 operator API가 인터넷에서 호출되지 않기를 원한다.
33. 운영자로서, 운영자 키와 마스터 키가 계정 서비스 컨테이너에만 있고 릴레이
    컨테이너에는 없기를 원한다.
34. 운영자로서, 계정 서비스 DB가 별도 데이터베이스라 나중에 다른 서버로 옮길
    수 있기를 원한다.
35. 운영자로서, psql로 계정과 커뮤니티 목록, 가입 시각을 조회할 수 있기를
    원한다.
36. 운영자로서, 분실 기기의 세션을 서버에서 끊을 수 있기를 원한다(SQL로
    충분).
37. 운영자로서, `.env`와 Postgres만 백업하면 서비스 전체를 복구할 수 있기를
    원한다.
38. 운영자로서, 계정 서비스 이미지가 릴레이와 같은 파이프라인으로 빌드·배포
    되기를 원한다.
39. 운영자로서, 계정 서비스 주소가 빌드에 없는 upstream 데스크톱은 지금과
    똑같이 동작하기를 원한다(upstream 머지 안전).

### 신뢰와 안전

40. 사용자로서, 코드 메일이 스팸함이 아니라 받은편지함에 오길 원한다.
41. 공격자가 아닌 사용자로서, 남이 내 이메일로 코드를 마구 요청해도 내
    계정에 들어올 수 없어야 한다(코드는 메일 수신자만 앎, 시도 5회 제한).
42. 사용자로서, 계정 서비스 DB가 유출되어도 내 신원 키가 평문으로 나오지
    않기를 원한다.

## Implementation Decisions

### 전체 구조

- 새 Rust crate `buzz-account`를 워크스페이스에 추가한다. 릴레이 crate는
  수정하지 않는다. upstream과 겹치는 파일은 루트 워크스페이스 members 한
  줄뿐이다.
- 계정 서비스는 같은 VPS의 compose 스택에 서비스 하나로 추가된다. 같은
  Postgres 인스턴스의 별도 데이터베이스를 쓴다. 릴레이는 Docker 내부 주소로
  호출한다.
- 공개 호스트는 `auth.app.pegboard.me` 하나. 그 외 `*.app.pegboard.me`는
  전부 릴레이로 간다.
- 팀 릴레이 `app.pegboard.me`는 그대로 멀티테넌트 릴레이가 된다. 전환 시
  Postgres를 비우고 `RELAY_OWNER_PUBKEY`와 `BUZZ_RELAY_PRIVATE_KEY`만 유지한다.
  릴레이에 `BUZZ_MAX_COMMUNITIES_PER_OWNER=1`, `RELAY_OPERATOR_PUBKEYS`(계정
  서비스 운영자 키), `RELAY_OPERATOR_API_ORIGIN`(내부 주소)을 설정한다.

### 계정 서비스 API (모두 JSON, HTTPS)

- `POST /v1/login/start` — 입력: email. 6자리 코드를 만들어 해시만 저장(만료
  10분, 시도 0/5), Resend로 발송. 같은 이메일은 분당 1회. 응답은 이메일
  존재 여부를 드러내지 않는다.
- `POST /v1/login/verify` — 입력: email, code. 성공 시 계정이 없으면 생성하고
  신원 키를 발급·암호화 저장. 응답: 세션 토큰(90일), 신원 키(nsec), 계정의
  커뮤니티 목록(host, role). 실패 시 남은 시도 횟수. 5회 실패 또는 만료 시
  코드 폐기.
- `GET /v1/me` — 세션 토큰. 응답: email, pubkey, 커뮤니티 목록, 생성 가능
  여부.
- `POST /v1/communities/check` — 입력: name. 정규화 결과와 가용성. 릴레이
  availability API를 대신 호출한다.
- `POST /v1/communities` — 입력: name. 계정당 1개 검사 후 릴레이
  `/operator/communities`를 `create_only: true`, `initial_owner_pubkey` =
  계정 pubkey로 호출. 응답: host, 릴레이 URL(`wss://<host>`). 릴레이 실패는
  그대로 오류로 전달하고 계정 서비스에 커뮤니티 행을 남기지 않는다(원자성).
- `POST /v1/logout` — 세션 폐기.
- `GET /v1/hosts/check?host=` — Caddy on-demand TLS의 `ask` 엔드포인트.
  `auth.app.pegboard.me`, `app.pegboard.me`, 그리고 계정 서비스가 만든
  커뮤니티 호스트만 200. 인증 없음, 응답 본문 없음.
- `GET /_readiness` — DB 연결 확인.

### 이름 규칙

- 정규화: trim → 소문자 → 공백을 하이픈으로 → 연속 하이픈 축약.
- 검증: `^[a-z0-9]([a-z0-9-]{1,28}[a-z0-9])?$`, 예약어 목록 거부.
- 커뮤니티 표시 이름은 입력값 그대로. host는 `<name>.app.pegboard.me`.

### 신원 키와 비밀

- 신원 키는 계정 서비스가 `nostr` crate로 생성한다. 저장은 AES-256-GCM,
  키는 환경변수 `ACCOUNT_MASTER_KEY`(32바이트 base64). nonce는 행마다 저장.
- 운영자 키는 환경변수 `ACCOUNT_OPERATOR_SECRET_KEY`. NIP-98 서명은
  `buzz-auth`의 기존 구현을 쓴다.
- Resend API 키 `RESEND_API_KEY`, 발신 `noreply@pegboard.me`. HTTP API를
  `reqwest`로 직접 호출한다. SDK 없음.
- 세션 토큰은 임의 32바이트, DB에는 해시만.
- 코드는 6자리 숫자, CSPRNG. DB에는 해시만.

### 스키마 (계정 서비스 DB)

- `accounts(id, email unique, pubkey unique, encrypted_secret_key, key_nonce,
  created_at)`
- `login_codes(id, email, code_hash, expires_at, attempts, consumed_at,
  created_at)` — 이메일당 최신 1건만 유효.
- `sessions(id, account_id, token_hash, expires_at, revoked_at, created_at)`
- `communities(id, account_id unique, name, host unique, relay_community_id,
  created_at)` — `account_id unique`가 계정당 1개를 강제한다.

### 데스크톱

- 빌드 환경변수 하나(계정 서비스 URL)로 분기한다. 비어 있으면 upstream
  온보딩이 그대로 나온다. 분기 지점은 기기 온보딩 진입 한 곳이다.
- 우리 온보딩은 새 feature 디렉터리에 새 파일로 둔다: 이메일 입력 → 코드
  입력 → (커뮤니티 없음) 만들기/초대 링크 화면 → 접속. 기존 upstream 파일
  수정은 진입 분기와 BuilderLab 클라이언트 교체로 제한한다.
- BuilderLab 클라이언트(Tauri 커맨드와 프런트 API)는 계정 서비스용으로
  바꾼다: 브라우저 로그인 대신 이메일/코드 커맨드, 커뮤니티 생성은 이름
  하나. 보관/이전 커맨드는 제거하지 않고 미노출로 둔다.
- 로그인 응답의 nsec은 기존 키체인 저장 경로로 커밋한다. 이미 키가 있으면
  덮어쓴다.
- 세션 토큰은 키체인의 같은 JSON 블롭에 함께 둔다.
- 커뮤니티 생성 성공 후는 upstream 흐름을 그대로 탄다: 로컬 목록 추가 →
  접속 → 프로필 → 스타터 채널 생성 → 환영 채널.
- 초대 링크로 앱을 열면 기존 대기 게이트가 로그인 뒤 조인을 이어간다.
- 설정에서 키 내보내기·가져오기·페어링 카드·"기존 키 사용"은 우리 분기가
  켜져 있을 때 렌더링하지 않는다.
- 커뮤니티 나가기는 upstream의 탈퇴 요청을 그대로 쓴다. UI에 없으면 추가한다.

### 인프라

- Cloudflare: `*.app.pegboard.me` A 레코드(proxy OFF), Resend가 요구하는
  SPF/DKIM/DMARC 레코드.
- Caddy: `app.pegboard.me`와 `*.app.pegboard.me`를 on-demand TLS로 받고
  `ask`를 계정 서비스의 hosts/check로 지정. `auth.app.pegboard.me`만 계정
  서비스로, 나머지는 릴레이로 reverse_proxy. 릴레이의 `/operator/*`는 Caddy
  에서 차단한다.
- compose: `account` 서비스 추가, 이미지는 `ghcr.io/nostrss/buzz-account:deploy`.
  docker.yml에 빌드 잡 추가. `run.sh upgrade`가 함께 올린다.
- 전환 런북(수동): `.env` 백업 → Postgres 덤프 → 컨테이너 중지 → 릴레이 DB
  초기화 → 새 `.env` 값 → `run.sh upgrade` → `app.pegboard.me` 커뮤니티를
  계정 서비스로 생성 → 팀원 재가입.

## Testing Decisions

좋은 테스트는 외부에서 보이는 동작만 검증한다. 계정 서비스는 HTTP 요청과
응답, DB에 남은 행, 밖으로 나간 HTTP 호출(Resend, 릴레이)만 본다. 데스크톱은
화면에 보이는 것과 Tauri 커맨드 호출만 본다.

### 경계 1: 계정 서비스 HTTP API

- 실제 Postgres에 대고 axum 라우터 전체를 띄운다. 릴레이의 sqlx 기반
  핸들러 테스트와 `buzz-test-client`가 선례.
- Resend와 릴레이 operator API는 테스트 내 가짜 HTTP 서버로 대체하고, 받은
  요청을 기록해 검증한다.
- 검증 항목: 코드 발송 시 이메일 존재 여부 미노출, 분당 1회 제한, 코드 해시
  만 저장, 5회 실패 시 폐기, 만료 시 거부, 첫 로그인 시 키 발급, 재로그인
  시 동일 pubkey, 저장된 키가 암호문, 세션 90일, 로그아웃 후 세션 무효,
  이름 정규화·검증·예약어, 계정당 1개 제한, 릴레이 호출 본문(create_only,
  owner pubkey, host), 릴레이 실패 시 커뮤니티 행 미생성, hosts/check가
  등록된 호스트만 200.

### 경계 2: 데스크톱 Tauri IPC (mock bridge)

- 기존 mock bridge에 계정 서비스 커맨드 스텁을 추가하고 Playwright smoke
  스펙을 쓴다. `installMockBridge`와 기존 smoke 스펙이 선례.
- 검증 항목: 분기 켜짐 시 첫 화면이 이메일 입력이고 키 관련 문구가 없음,
  코드 입력 오류 표시, 커뮤니티 없음 화면의 두 카드, 이름 입력 시 미리보기와
  가용성 표시, 생성 후 환영 채널 진입, 초대 링크 대기 후 자동 조인, 설정에
  키 관련 카드 미노출, 분기 꺼짐 시 upstream 온보딩 그대로.

### 검증하지 않는 것

- 릴레이: 코드 변경 없음. 기존 테스트로 충분.
- Caddy/DNS/Resend 실제 발송: 전환 런북의 수동 확인 항목.
